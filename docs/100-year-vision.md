# Kaname 100 年保守ビジョン

> "It's really hard to design products by focus groups. A lot of times, people don't know what they want until you show it to them."  
> — Steve Jobs

このドキュメントは Kaname を **100 年運用する** ための長期方針を定義する。

通常のソフトウェアは 5 年で陳腐化する。Apple の Macintosh が 1984 年に登場して 42 年経つが、未だに「Mac」というブランド名で動き続けているのは設計思想に長期視点があったから。Kaname は **2026 年に始まり、2126 年も動き続ける** ことを目指す。

---

## 100 年存続の 3 つの保証

### 1. 暗号アルゴリズムの世代交代に備える

```
2026: ML-KEM-768 + X25519           (現在)
2030: 量子コンピューター実用化       → X25519 廃止予定
2040: ML-KEM 自体が破られる可能性    → 第二世代 PQC 導入
2050: 第二世代ポスト量子暗号への移行
2100: 現在予測不能な暗号             → 新世代に交換可能な抽象化
```

**設計**: `kaname-crypto` の `Suite` トレイトでアルゴリズムを抽象化。
具体実装はビルド時 feature フラグで切り替え可能。

```rust
pub trait CryptoSuite {
    type PublicKey;
    type SecretKey;
    fn key_gen() -> (Self::PublicKey, Self::SecretKey);
    fn encrypt(pk: &Self::PublicKey, msg: &[u8]) -> Vec<u8>;
    fn decrypt(sk: &Self::SecretKey, ct: &[u8]) -> Vec<u8>;
}

// 2026: ML-KEM-768 + X25519
// 2050: 次世代 PQC に交換
// 暗号アルゴリズムの「正面玄関」(API) は変えない
```

### 2. 言語・ランタイムの世代交代に備える

```
2026: Rust 1.82                    (現在)
2050: Rust 4.x                     (予測)
2100: 完全に新しい言語             (?)
```

**原則**:
- `unsafe` 禁止 (`#![deny(unsafe_code)]`)
- 標準ライブラリ重視、外部依存最小化
- 各クレートは「100 年後でも仕様書だけで再実装可能」な明文化された API を持つ
- `docs/specifications/` に各クレートの「言語非依存仕様」を保管

### 3. 依存ライブラリの世代交代に備える

**現在の依存**: 約 200 個 (Cargo.lock)

**100 年原則**:
- 各依存に「代替候補」を `docs/dependency-alternatives.md` に記録
- 1 つの依存が消滅しても 1 週間以内に代替できる体制
- 商用ライブラリは依存しない (会社が消滅するリスク)
- IETF / ISO / NIST 等の **標準仕様に基づく実装のみ**を選ぶ

```
ライブラリが消えても Kaname は生きる:
  reqwest → hyper → http (標準仕様)
  serde   → 自前実装 (型情報を変えない)
  tokio   → glommio / smol → std::thread
```

## 形而上の設計原則 (100 年変えない)

### 原則 1: ローカルファースト

サーバー側で動く機能をクライアントに移せるなら移す。理由: サーバーは 100 年後には消えている (運営会社の存続が保証されない)。

**反例 (絶対にやらない)**:
- AI 推論をクラウドで実行 (Anthropic / OpenAI のサービスが終了したら全機能停止)
- ライセンス検証をオンライン必須にする (Stripe が 100 年後に存在する保証はない)

**Kaname の選択**:
- AI 推論はローカル (Phi-4-mini はオンプレで永続実行可能)
- ライセンスは **オフラインで検証できる Ed25519 署名トークン** (Stripe が消えても動く)

### 原則 2: 標準仕様の絶対優先

> 独自プロトコル < 業界標準 < IETF RFC < ISO 標準

**Kaname の選択**:
- メールプロトコル: JMAP (RFC 8620/8621) — IMAP より新しいが標準
- 暗号: MLS (RFC 9420)、TLS (RFC 8446)、ML-KEM (FIPS 203)
- ファイル: MIME (RFC 2045-2049)
- 国際化: BCP 47、Unicode、CLDR

**反例**: Slack のメッセージ形式は独自 → 100 年後に解読できない可能性

### 原則 3: ユーザーのデータを人質にしない

**Apple 流の Kaname 適用**:
- エクスポート機能を最初から実装 (mbox、JSON、CSV)
- データ形式は仕様文書化 (Kaname なしで読める)
- 移行ツールを公式提供 (FastMail、Proton 等への一括エクスポート)

> 「ユーザーが Kaname を使い続けるのは便利だから」であって「乗り換えできないから」ではない

### 原則 4: 機能は減らす方向にも進化する

```
v1.0 → v2.0 → v3.0 → v4.0
機能数: 100 → 95 → 90 → 80
```

Apple の iWork、Final Cut Pro、Aperture などは過去にメジャー版で機能を**減らして**再設計した。Kaname も同様に「複雑になりすぎたら削る」覚悟を持つ。

### 原則 5: ブランドは個人を超える

100 年保守には個人の死を超える組織設計が必要。

```
2026: 創業者世代
2050: 第二世代 (後継者)
2075: 第三世代
2100: 第四世代
```

**仕組み**:
- BDFL (Benevolent Dictator) ではなく「DRI ローテーション」
- 5 年ごとに組織レビュー (`docs/governance-review-2030.md` 等)
- 創業者の決定はすべて文書化、後継者が読める形で残す

## 5 年マイルストーン (現実的な実行計画)

### v1.0 (2026 年): Foundation
- Dual-LLM 型安全コア
- MLS RFC 9420 + ML-KEM-768
- BEC 検出、AI 生成フィッシング検出
- macOS / Windows / Linux ネイティブアプリ

### v2.0 (2028 年): Mobile + Mature
- iOS / Android アプリ (同じ Rust コアを wasm/jni で再利用)
- 30 社の Design Partner で実証済み
- App Store Notarization 完了

### v3.0 (2031 年): Quantum Migration
- 第二世代 PQC への移行
- 古い MLS グループのアップグレード自動化
- 量子コンピューター時代の脅威モデル更新

### v4.0 (2036 年): AI Generation Shift
- Phi-4-mini 後継モデル (Phi-7-nano など) への移行
- ローカル推論の高速化 (専用 NPU 活用)
- Apple Silicon M5 / M6 世代最適化

### v5.0 (2046 年): Generation Handover
- 創業者世代から第二世代への完全移行
- ガバナンスのレビュー
- 100 年計画の中間検証

### v10.0 (2076 年): Half-Century Milestone
- 50 年運用の歴史的検証
- 当初の北極星 (AIが助けても裏切らない) が依然有効か再評価
- 必要なら新たな北極星を策定

### v20.0 (2126 年): Centennial
- 100 年運用達成
- アーカイブと教訓の総括
- 次世代への伝承

## 撤退・解散プロトコル

100 年運用するつもりでも、解散する可能性に備える。

### 解散時の責務

1. **ユーザーデータ**: 30 日前にアナウンス、エクスポート機能を最後まで提供
2. **ソースコード**: AGPL-3.0 のため公開状態を維持、フォーク可能性を保証
3. **暗号鍵**: HSM の鍵をフォークコミュニティに委譲する手順を事前文書化
4. **ライセンス**: ユーザーは購入時の機能を**永久に**使える (オフライン検証で動く)

### 「Kaname の死」が他の生き方を妨げないように

- Stripe 連携が切れても、Kaname のコア機能は動き続ける
- ライセンスチェックはオフライン (運営会社が消えても問題なし)
- ユーザーデータの所有権は完全にユーザー側

## 反 100 年原則 (避けるべきパターン)

### ❌ 「最新技術への盲従」

例: WebAssembly が流行ったから AI を WASM で動かす  
→ WASM は 100 年後に存在するか不明。ネイティブプロセスのほうが堅牢。

### ❌ 「Move fast and break things」

Facebook の標語は「破壊することで進化する」。Kaname は逆。  
**「動き続けるものを作り、破壊しない」**

### ❌ 「全員のための機能」

100 人 中 99 人が使わない機能は載せない (Apple 流: Less is more)。  
99 人のために UI を複雑化すれば、100 人目 (ヘビーユーザー) も逃げる。

### ❌ 「依存ロックイン」

特定のサービス (AWS、Google Cloud、Anthropic API 等) に依存しない。  
すべての外部サービスは「いつでも交換可能」な抽象層の背後に隠す。
