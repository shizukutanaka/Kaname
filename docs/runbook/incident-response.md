# インシデント対応ランブック

> このドキュメントは Kaname のセキュリティインシデント発生時の対応手順を定義する。

---

## SEV (深刻度) 定義

| SEV | 定義 | 初回応答 | 解決目標 |
|---|---|---|---|
| **SEV 1** | 全停止 / データ損失 / 重大なセキュリティ侵害 | 15 分以内 | 4 時間 |
| **SEV 2** | 主要機能停止 / 脆弱性の悪用確認 | 1 時間 | 24 時間 |
| **SEV 3** | 一部不具合 / 未悪用の脆弱性発見 | 4 時間 | 72 時間 |
| **SEV 4** | 軽微 / UX の問題 | 翌営業日 | 次スプリント |

---

## SEV 1 対応フロー

```
1. アラート受信
   ↓
2. DRI を叩き起こす (24/7)
   ↓
3. 影響範囲を 15 分以内に評価
   ↓
4. ロールバックを最初の選択肢として検討
   │
   ├─ ロールバック可能 → 即時実行 → ポストモーテム
   │
   └─ ロールバック不可 → ホットフィックス → リリース → ポストモーテム
```

---

## セキュリティインシデント固有の手順

### プロンプト注入が疑われる場合

1. 影響を受けたユーザーの AI 監査ログを確認 (`kaname-store` の audit_log テーブル)
2. `AiAccessController::verify_chain()` でハッシュチェーンの完全性を検証
3. Q-LLM のサブプロセスログを確認 (seccomp 違反があれば侵害の証拠)
4. Content<Untrusted> → Content<Trusted> の変換記録を確認
5. Bridge の attack_markers リストを更新してデプロイ

### BEC 詐欺被害が報告された場合

1. 被害者のメールの `kaname-bec` スコアを再計算
2. 攻撃者ドメインを `PhaaS インフラリスト` に追加
3. `kaname-radar` のキャンペーングループを確認 (同一インフラから他のユーザーへの攻撃がないか)
4. 関連する PCR グループを法執行機関のために保存 (30 日の retention を延長)

### Deepfake 詐欺が報告された場合

1. OOBV の監査ログを確認 (攻撃者が正しいワードを答えたかどうか)
2. 被害発生時刻付近のセレモニー記録を保全
3. `attack_markers` の追加を検討
