# 削った 1000 の機能 — Apple 流「No」の記録

> "I'm as proud of many of the things we haven't done as the things we have done.
> Innovation is saying no to a thousand things."  
> — Steve Jobs (1997)

このドキュメントは Kaname が**意図的に断った**機能を記録する。

「やらないこと」を明文化することで、北極星 (AIが助けても裏切らない) が薄まらないように守る。**機能を追加する PR を出す前に、ここに同じものが既に却下されていないかを確認する**。

---

## 北極星 (再確認)

**「AIが助けても裏切らない、唯一の法人向けセキュアメールクライアント」**

3 本柱: Security / Speed / Privacy  
それ以外を最大化する機能は、原則として却下する。

---

## カテゴリ A — 機能の追加を断った決定

### A-1. チームコラボレーション機能 ❌ NO
**例**: Slack 風メッセージング、共有フォルダ、コメント、タスク管理

**理由**:
- メールクライアント本来の責務から外れる
- Slack/Teams が既に圧倒的な解決策を持っている
- 攻撃面を不必要に増やす (XSS、データ漏洩経路)
- 開発リソースが分散し、北極星が薄まる

**代替**: Slack/Teams 等への通知を Tauri Plugin で実装可能 (オプション)

### A-2. カレンダー統合 ❌ NO (v1.0 では)
**例**: 内蔵カレンダー、ミーティング自動作成、出席者管理

**理由**:
- 別アプリ (Apple Calendar / Google Calendar) で十分
- ICS ファイル添付の自動展開だけで 80% のユースケース対応可能
- カレンダー実装は 6 ヶ月のフルタイム開発が必要

**v2.0 で再評価**: ICS 展開は実装するが、独立カレンダー機能は実装しない

### A-3. マルチアカウント切り替え ❌ NO (v1.0 では)
**例**: 複数 Gmail / Outlook / 個人 + 仕事の同時表示

**理由**:
- セキュリティモデルが複雑化 (Q-LLM がどのアカウントを「単一メール」と見なすか?)
- UI が複雑化 (HEY も最初は単一アカウントのみ提供)
- 法人ユースケースでは「仕事メール」だけで十分

**v2.0 で再評価**: 法人内の複数役職切り替えとして検討

### A-4. RSS / ニュースリーダー機能 ❌ NO
**例**: Feedly 風 RSS リーダー、ニュースアグリゲーション

**理由**:
- メールクライアントとは異なる UX を必要とする
- RSS は OS 全体の問題 (各アプリが個別に解決すべきでない)

### A-5. ウィジェット / Apple Watch アプリ ❌ NO (v1.0 では)
**例**: macOS ウィジェット、Watch 通知、CarPlay 連携

**理由**:
- セキュリティ上、メール本文がウィジェットに表示されると危険
- Watch の小さい画面で重要メールを判断するのは BEC リスクを増やす
- まず本体アプリの完成度を高める

**v2.0 で再評価**: 「未読数だけ」表示するウィジェットは検討

## カテゴリ B — 設計の選択肢を断った決定

### B-1. 「すべての AI モデル選択肢」 ❌ NO
**例**: ユーザーが OpenAI / Anthropic / Local / Custom を選べる

**理由**:
- セキュリティ保証が複雑化
- ローカル AI のみが「データがデバイスを離れない」を保証できる
- ユーザーは「正しい選択」を強要されるべきではない (Apple 流: We choose for you)

**実装**: Phi-4-mini Q4_K_M ローカル固定。代替モデルは v3.0 で「上級者向け設定」

### B-2. プラグイン / 拡張機能エコシステム ❌ NO
**例**: VS Code 風プラグイン、ユーザースクリプト

**理由**:
- プラグインがプロンプト注入を引き起こす (Superhuman CVE と同じ機序)
- セキュリティモデルが破綻する
- App Store 審査が複雑化

**代替**: 設計レベルの拡張ポイント (DLP ルール追加等) のみ提供

### B-3. PGP / S-MIME サポート ❌ NO
**例**: Enigmail 風 PGP、S-MIME 証明書管理

**理由**:
- PGP は 30 年間ユーザビリティ問題が解決していない
- 件名が平文のまま漏洩する (致命的欠陥)
- MLS RFC 9420 が技術的にも UX 的にも優れている
- 後方互換のための実装は北極星を薄める

**実装**: MLS のみ。PGP メールを受信した場合は「読み取り専用、暗号は表示のみ」

### B-4. Web 版アプリ ❌ NO
**例**: ブラウザで動く SaaS 版 Kaname

**理由**:
- ローカル AI 推論が事実上不可能 (大型モデルをブラウザにロードできない)
- ファイルシステム・OS Keychain アクセスができない
- セキュリティ境界がブラウザに依存 (Kaname の保証より弱い)

**代替**: モバイル版 (iOS / Android) は v2.0 で検討

### B-5. 「ベータ版での収益化」 ❌ NO
**例**: 早期アクセスを高額で販売、機能制限版を Free で配布

**理由**:
- v1.0 完成前の収益化は信頼を毀損する
- 「Security のために金を払う」は不自然な訴求 (Apple 流: 体験で売る)

**実装**: v1.0 まで完全無料、Design Partner 30 社で長期検証してから有料化

## カテゴリ C — UX の選択肢を断った決定

### C-1. ダッシュボード画面 ❌ NO
**例**: 統計、グラフ、メール件数の可視化

**理由**:
- Apple HIG: 「ユーザーは最頻のタスクをすぐ実行したい」
- メールクライアントの最頻タスク = 受信トレイを開く
- ダッシュボードは 3 秒の余分なコストを毎回発生させる

### C-2. 「Mark as Important / 重要マーク」機能 ❌ NO
**例**: Gmail 風の重要度マーカー

**理由**:
- HEY が証明済み: ユーザーは Important を判断しない
- AI が自動判定 (TriageEngine) するほうが正確
- 機能を増やすたびに学習コストが増える

### C-3. テーマカスタマイゼーション (色・フォント) ❌ NO
**例**: ダークモード以外のカラースキーム選択、フォント自由設定

**理由**:
- アクセシビリティ (WCAG AAA) を維持できない
- ブランド一貫性が失われる (Apple 流: We design for you)

**実装**: ライト / ダーク / High Contrast の 3 モードのみ (OS 設定追従)

### C-4. アニメーション設定 ❌ NO
**例**: 「アニメーションを早く / 遅く」設定スライダー

**理由**:
- `prefers-reduced-motion` で OS から取得すべき
- ユーザーが調整する必要のない領域

### C-5. 「永久ゴミ箱」機能 ❌ NO
**例**: 削除メールを完全消去せず別フォルダに保管

**理由**:
- GDPR 「忘れられる権利」と矛盾
- ストレージリーク
- ユーザーの「捨てた」期待を裏切る

**実装**: 30 日後の自動削除のみ。手動「完全削除」も可

## カテゴリ D — 技術選択を断った決定

### D-1. Electron ❌ NO → Tauri
**理由**: 200MB のバイナリサイズ、Chromium 起動コスト、セキュリティ面の劣化

### D-2. JavaScript / TypeScript の Backend ❌ NO → Rust
**理由**: 型安全性 (Phantom Type の `Content<Untrusted>` が JS では不可能)、メモリ安全、性能

### D-3. ReactPak / Vue ❌ NO → SolidJS
**理由**: バンドルサイズ (gzip < 8KB)、Reactivity がメンタルモデルとして優れる

### D-4. PostgreSQL / MongoDB ❌ NO → SQLCipher (SQLite + AES-256)
**理由**: ローカルファースト、サーバー不要、暗号化標準装備

### D-5. WebAssembly での AI 推論 ❌ NO → ネイティブプロセス
**理由**: WASM では大型モデルが載らない (4GB メモリ制限)、性能不足

---

## カテゴリ E — マーケティング選択を断った決定

### E-1. 「AI を強調する」マーケティング ❌ NO
**例**: "Powered by AI"、"Smart" バッジ、AI 機能の前面押し出し

**理由**:
- AI は手段、目的ではない
- 「AI が安全」が訴求点であって「AI 搭載」が訴求点ではない
- 競合 (Superhuman) が AI を強調してプロンプト注入で炎上

**実装**: AI は静かに動く。UI で目立たせない。

### E-2. 価格の早期公開 ❌ NO
**理由**: 機能完成前の価格議論は本質を逸らす

**実装**: Design Partner 30 社の検証データを揃えてから価格設定

### E-3. プレスリリース重視 ❌ NO
**理由**: TechCrunch の称賛より、実ユーザーの「これがないと困る」が信頼度の指標

**実装**: 30 社の Case Study + 公開 Security Report を優先

## 機能追加を提案する人へ

PR / Issue でこのドキュメントに該当する却下案を提案する場合:

1. **既存の却下理由が現在の状況で変わったか**を明示
2. **北極星 (Security / Speed / Privacy) が改善する**ことを論証
3. **代替案 (この機能を作らずに同じ価値を提供する方法)** が存在しないことを示す

満たさない場合、メンテナーは即座にクローズします。
