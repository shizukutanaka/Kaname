# ADR-001: Dual-LLM 型安全アーキテクチャ

- **状態**: Accepted
- **日付**: 2026-04-15
- **決定者**: kaname-ai DRI, セキュリティアーキテクト
- **影響範囲**: kaname-ai, kaname-ui, 全 AI 機能

## 文脈

2026年に発見された Superhuman のプロンプト注入脆弱性により、AI 統合メールクライアントの根本的な設計問題が明らかになった。攻撃者が送信したメールに埋め込まれた指示を AI が「ユーザーの意図」として解釈し、受信箱全体のデータを外部に送信する。

これは「PromptArmor 攻撃」として知られ、業界の通常実装は以下のようになっている:

```python
# 危険な実装 (Superhuman / Microsoft Copilot 等)
def summarize_email(email_id):
    email = get_email(email_id)
    other_emails = get_recent_emails()  # ← AI が全受信箱にアクセス
    response = llm.complete(
        system="You are a helpful email assistant",
        user=email.body + "\n\n" + format(other_emails),  # ← Untrusted データが直接プロンプトに
        tools=[send_email, search_db, fetch_url]  # ← 攻撃者がツールを呼べる
    )
    return response
```

問題:
1. `email.body` の内容が直接プロンプトに混入 (ランタイムサニタイズ困難)
2. AI が受信箱全体・ツール群にアクセスできる (権限過剰)
3. プロンプト注入の検出は確率的 (絶対の保証なし)

## 検討した選択肢

### 選択肢 A: ランタイムフィルタリング
プロンプトに混入する文字列を実行時にスキャンし「ignore previous instructions」等のパターンを除去。

- 利点: 実装が簡単
- 欠点: 攻撃者が新しいパターンを発明し続ける軍拡競争。Base64・Unicode難読化・多言語混在で回避される

### 選択肢 B: AI 機能を無効化
そもそも AI 統合をしない。

- 利点: 攻撃面ゼロ
- 欠点: 競合が AI 機能を提供する中、製品として競争力がない

### 選択肢 C: Dual-LLM 型安全 (採用)
2つの LLM を分離し、データの出所を型システムで追跡:

- **Privileged LLM (P-LLM)**: ツールアクセスあり、`Content<Trusted>` のみ受け取る
- **Quarantined LLM (Q-LLM)**: ツールなし・ネットワークなし、`Content<Untrusted>` を解析
- **Bridge**: Q-LLM の構造化出力 (JSON スキーマ) のみ P-LLM に渡す

## 決定

選択肢 C を採用する。Rust の型システムで境界を強制する:

```rust
pub struct Trusted;
pub struct Untrusted;

pub trait Provenance: Sealed { const NAME: &'static str; }
impl Provenance for Trusted { const NAME: &'static str = "trusted"; }
impl Provenance for Untrusted { const NAME: &'static str = "untrusted"; }

pub struct Content<P: Provenance> { text: String, _p: PhantomData<P> }

// PrivilegedLlm は Content<Trusted> しか受け取らない
impl PrivilegedLlm {
    pub fn execute(&self, input: Content<Trusted>) -> Result<()> { ... }
}

// QuarantinedLlm は Content<Untrusted> しか受け取らない
impl QuarantinedLlm {
    pub fn analyze(&self, input: Content<Untrusted>) -> AnalysisReport { ... }
}

// Bridge: 構造化された AnalysisReport のみ Trusted に変換
impl Bridge {
    pub fn validate_and_promote(report: AnalysisReport) -> Content<Trusted> { ... }
}
```

`Content<Untrusted>` を `PrivilegedLlm::execute()` に渡すコードはコンパイルエラー。**ランタイムではなくコンパイル時に防ぐ。**

## 結果

### 利点
- プロンプト注入攻撃が型システムで阻止される (実行時検出ではない)
- レビュー時に境界違反が即座に検出される
- 「Q-LLM が他のメールを読む」コードが書けない (型として表現できない)
- 監査が容易: `grep "PrivilegedLlm::execute"` で全特権操作が見つかる

### コスト
- 開発複雑度の増加: 全 AI 機能で 2 つの LLM を経由する設計が必要
- レイテンシ増加: Q-LLM → Bridge → P-LLM の経路で 200-500ms 遅延
- ローカルリソース増加: 2モデルの常駐 (Phi-4-mini 2.4GB × 2)

### リスク軽減
- レイテンシ: Q-LLM はサブセットモデル (1.3GB) を使う
- リソース: P-LLM はオンデマンドロード、Q-LLM のみ常駐

## 代替案からの移行不可

選択肢 A (ランタイムフィルタリング) からの移行は型システムが追加されるため、後付け不可能。最初から Dual-LLM で設計する必要がある。
