# ソクラテス問答による製品レビュー (2026-07)

イーロン・マスクのアルゴリズム (要件を疑う→削除→簡素化→組み立て) に加え、
**ソクラテス問答法** (前提を問い直す自問) で Kaname を批判的に吟味した記録。
誇張せず、実コードの根拠に基づいて長所・短所・改善点を並べる。

---

## Q1: この製品は「メールクライアント」と呼べるか?

**A**: 呼べる。v0.5.0 で受信 (`mail_fetch`) → 保存 (`save_message`) →
表示 (`sanitize_html`→`to_srcdoc`) → 送信 (`mail_send`, 送信前 DLP) →
検索 (`mail_search`) → 添付ダウンロード (`mail_download_attachment`) が
すべて配線された。ローカル `.eml` 解析はサーバなしでも動く。

**ただし**留保がある: 中核の暗号 (MLS) と LLM 推論はモック/スタブ (D1/D2)。
「セキュア**メール**クライアント」の「メール」部分は成立したが、
「セキュア」の暗号面は未達。→ 名乗るなら「**メールセキュリティ解析ツール
+ 実験的メールクライアント**」が正確。

## Q2: 「セキュリティ」は本物か、それとも見せかけか?

**A**: 検出ロジックは**本物**。BEC (9 決定論シグナル)・DLP・quishing・
添付検査 (MIME偽装/polyglot/危険拡張子/SVG/カレンダー)・リンク評判・
文体認証・トラッキング検出は、すべて実データで動き、判定に乱数も
固定値もない。サンプル `examples/emails/` で誰でも再現できる。

**見せかけの部分**: Dual-LLM の型境界は「定義は堅牢だが実装が通っていない」
(D17)。現状 LLM 経路が繋がっていないので悪用余地は無いが、
**LLM を繋ぐ前に D17 を塞がないと型保証が名ばかりになる**。

## Q3: 最大の弱点は何か?

**A**: **一度も `cargo check` を通していない** (D20)。
組織のエグレスポリシーで `static.crates.io` が遮断され、依存を取得できない。
`rustc` 直接実行による構文チェックと `scripts/static-check.sh` までが限界で、
借用チェッカ・トレイト解決・テストは未検証。

この穴は**実害を生んだ**: PR #64 の編集で関数が定義ごと消え、
コンパイルエラーの状態が 5 PR 検出されなかった (PR #70 で修正)。
→ これは製品の設計欠陥ではなく**環境制約**。ただしリリース品質を
主張するには型検査が必須であり、ネットワーク解放が最優先の残課題。

## Q4: 「完成」とは何を指すべきか?

**A**: 環境制約下で到達可能な完成は
「**ローカルで実メールを解析でき、サーバ接続時は送受信・保存・検索・
添付取得も動く、正直なプレリリース**」。
配線 (D10) はこのフェーズで完全に閉じた。
残る D1 (MLS)・D2 (LLM)・D20 (型検査) は**いずれもネットワーク解放が前提**で、
その旨を `maturity.md` に明記している。**できることとできないことを
偽らずに示せている状態を「完成」と定義する**。

## 長所 (実コード根拠あり)

- 検出ロジックが世界水準かつ決定論的で、2026 年の最新脅威 (DKIM リプレイ・
  動的QR・SVG マルチモーダル注入・表示名ホモグラフ) を反映
- 「モックを本物と偽らない」規律: `kaname-mls`/`kaname-sandbox` を
  到達可能クレート数のために繋がず、暗号/隔離を装わない
- 判定不能を「安全」と偽らない (UNKNOWN / InsufficientData を SAFE にしない)
- 新規外部依存をほぼ増やさず (日付計算も自前)、攻撃面を広げていない

## 短所

- 型検査未実施 (D20、環境制約)
- MLS がモック・LLM がスタブ (D1/D2)
- Dual-LLM 型境界の実装が定義を通っていない (D17)
- 認証トークンを永続化しないため起動のたびに再接続が必要 (OS キーチェーン未統合)

## 改善点 (優先順)

1. **ネットワーク解放後に `cargo check --workspace` + `cargo nextest`** で
   本セッションの全コミットを一括検証 (D20)
2. **D17 を塞ぐ**: `llm_bridge` の実装を `dual_llm` の trait に載せ替え、
   `Content` の serde 偽造穴を閉じる — LLM を繋ぐ前に必須
3. **MLS を `openmls` で実装** (D1)、PQ ciphersuite を最初から選定
4. OS キーチェーン統合でトークンを安全に永続化

## 追加問答 (2026-09・フロントエンド到達可能性)

**Q: 「配線した」と言えるのは、いつか?**

A: 前セッションで「受信箱の検索欄を `mail_search` に接続した」「送信時に DLP が
ブロックする」と記録したが、**どちらもエントリポイントから到達できなかった**。
`Inbox.tsx` はどこからも import されておらず、受信トレイに実際に描画されていたのは
invoke を一切呼ばない `KanameDesign` だった。`mail_send` を呼ぶ画面も未到達だった。

つまり「コマンドを呼ぶコードを書いた」ことと「製品がそのコマンドを呼ぶ」ことは
別である。**「配線した」と言えるのは、エントリポイントからの到達可能性を実測した
ときだけ**である。クレートについては D19 で依存グラフを実測して同じ病を見つけて
いたのに、フロントエンドに同じ計測を適用していなかった。

**Q: なぜ同じ間違いを繰り返したのか?**

A: 計測の対象を「自分が今書いているレイヤー」に限定していたから。Rust 側の
到達可能性は測ったが、TypeScript 側は「ファイルが存在し、正しいコマンドを
呼んでいる」ことを確認して満足していた。**存在は到達可能性を意味しない。**

**Q: この発見は製品にとって良い知らせか、悪い知らせか?**

A: 良い知らせである。実装は既に存在し、欠けていたのは import 1 行と
引数の形だけだった。悪いのは**発見が遅れたこと**であって、実装ではない。
そして削除できるコードが 2,284 行見つかった — モック専用の画面 2 つは、
実データ版が動く以上、存在するだけで「どちらが本物か」を曖昧にする負債だった。

**Q: では今、UI は正直か?**

A: 一点、明確な嘘を見つけて直した。作成画面の MLS インジケータは宛先ドメインの
接尾辞 (`@kaname.app`) だけを見て「MLS 対応」と表示していたが、`kaname-mls` は
XOR モック (D1) であり、宛先が何であれ実際の暗号化は行われない。
**実装されていない保護を UI が「対応済み」と示すのは、検出ロジックの精度を
誇張するより悪い** — 利用者はそれを見て機微な情報を送るからである。常に
非対応を返すよう修正した。

オンボーディング画面を配線しなかったのも同じ理由による。`settings_save_onboarding`
はエラーを返すスタブであり、配線すれば「設定が保存できたように見えて失敗する」
画面になる。**保存できない設定画面は、無い方がよい。**

**Q: 到達可能にすれば十分か?**

A: 不十分だった。`Inbox` を出荷 UI にした直後に、その `Inbox` が呼ぶ 3 コマンドが
すべてスタブだと分かった。到達可能性は必要条件であって十分条件ではない。
検証は「エントリポイントから到達できるか」と「到達先が実装か」の**二段**で行う。
今回は「到達可能 UI が呼ぶコマンド ∩ `not_wired` スタブ」を機械的に求め、
空集合になるまで実装した。

副産物として、作成画面に定型文を「AI 草案」と称して挿入するボタンを見つけて
削除した。LLM がスタブである以上、それは AI 出力の偽装である。

**Q: 「実装した」と記録した永続化は、動いていたか?**

A: 動いていなかった。二重に。Store を開くコマンドはどの UI からも呼ばれておらず、
仮に開いても外部キー制約の前提となる `accounts`/`mailboxes` 行を作る本番コードが
無かった。「Store 未接続なら何もしない」「保存に失敗しても解析結果は返す」という
安全側の設計が、**欠陥を完全に隠していた**。エラーが出ないことは動いている証拠に
ならない。ログに warn は出ていたはずだが、誰も見ないログは無いのと同じである。

**Q: では完成とは?**

A: エントリポイントから到達可能な UI (9/9) が呼ぶコマンドがすべて実装
(`not_wired` 0 件) で、その実装が外部キーやセッション等の**前提条件を自分で満たす**
こと。今回の修正でその状態に達した。残るのは環境制約 (cargo 未検証・D20) と、
最初から「モック」と明示している MLS/LLM/サンドボックスであり、
それらは**製品が嘘をつかない限り**完成の定義に含めない。

## 追加問答 (2026-09・計測の自動化)

**Q: なぜ同じクラスの間違いを 4 回繰り返したのか?**

A: 毎回「その場で python を書いて測り、直したら測定を捨てていた」から。
死蔵コンポーネント・引数不一致・スタブ呼び出し・Store 未オープンは、
どれも**機械的に検出できたはずのクラス**である。人間の注意力に頼る限り、
次のセッションでまた見落とす。

マスクのアルゴリズムの第 5 段階「自動化」は、削除と簡素化が済んでから
行えという順序である。v0.6.0 でそれが済んだので、`scripts/static-check.sh`
に検査 3 (フロントエンド到達可能性)、検査 4 (invoke とコマンド定義の
名前・引数の整合)、検査 5 (登録済みだが呼ばれないコマンド) を恒久化した。

**Q: 自動化して、すぐ何か見つかったか?**

A: 実行した瞬間に 3 件見つかった。`AdminDashboard` は**どこからも描画されず**、
存在しない 3 コマンド (`admin_get_dashboard` ほか) を呼んでいた。
`mail_list` は**空配列を返す偽実装**で、呼び手はゼロだった。
どちらも削除した。ファイル単位の到達可能性 (検査 3) では見つからない、
**ファイルは到達可能だがコンポーネントは死んでいる**という細かい欠陥だった。

**Q: 「UI が呼ぶ先はすべて実装」で完成と言えるか?**

A: 言えない。逆方向を測っていなかった。検査 5 は、登録 37 コマンドのうち
**19 件が UI から呼ばれない**ことを示した (D24)。ただしその内訳は重要で、
10 件は LLM 依存であり、**LLM がスタブの現状で配線すれば偽の AI 出力を
表示することになる**。配線しないことが正しい。残り 5 件は配線すべきもの、
4 件は内部 API として正当なものである。

**完成とは「全部つながっている」ことではなく、「つながっていない箇所の
理由を全部言えて、その理由が正当である」ことだと考える。**

## 追加問答 (2026-09・検証ツール自体の欠陥)

**Q: `static-check.sh` は本当に安全網として機能していたか?**

A: していなかった。PR #86 で `mail_list` を削除した際、同じ関数を呼ぶ
テストが2件、コンパイルエラーのまま次のセッションまで残っていた。
`static-check.sh` の検査2はまさにこの種の回帰 (関数を削除したのに
呼び出しだけが残る) を検出するために作った検査だったが、実装が
**ハードコードされたシンボル一覧**しか見ておらず、一覧に `mail_list`
が無かったために素通りしていた。検証ツール自身が「一覧を都度手で足す」
という、検出したかった問題と同じ構造の脆さを抱えていた。

**Q: なぜ一般化を後回しにしていたのか?**

A: PR #71 で最初に作った時点では「今回壊れた具体的な関数名を拾えれば
十分」という最小実装で止めていた。その後 D21/D22/D24 の一連の配線作業で
検査3〜5を追加したが、検査2自体は一度も見直していなかった —
新しい種類の欠陥を追加するたびに検査を増やす一方、既存の検査の
弱点を遡って直す習慣がなかった。

**Q: 一般化したら何が起きたか?**

A: 最初の実装はリポジトリ全体で70件超の誤検知を出した。原因を1つずつ
潰す過程で、属性・raw文字列・char リテラル・行末コメント・複数行 import・
クロージャ束縛という6種類の見落としが見つかった。特に文字列内の
バックスラッシュ行継続 (`\` + 改行) を1箇所見逃しただけで、そこから
後のファイル全体で文字列の境界がズレるという、デバッグに最も時間を
要した種類のバグだった。**検証コード自体にも、検証すべきコードと
同じだけの注意が要る。**

## 追加問答 (2026-09・同じ欠陥がフロントエンドにもあった)

**Q: D25 (Rust 側の放置されたコンパイルエラー) を直した後、同じ穴が
フロントエンドにも無いか確認したか?**

A: していなかった。指摘されたわけではなく、「他に価値ある小さな改善は
ないか」と自分で探した結果見つかった。`app.test.ts` の `makeEmail()` は
`KanameApp.tsx` 削除時に一緒に消すべきだった死蔵コードで、しかも削除済み
の `Email` 型を import せず参照していた。`tsc`/`vitest` が動く環境なら
型エラーで即発覚するが、D20 (ネットワーク遮断) で3セッション気付かれ
なかった。

**Q: 検査を追加する際、最初の実装をそのまま信用したか?**

A: しなかった。D25 で「一般化した検査自体に見落としがないか、合成的に
既知のバグを再現して確認する」という手順を身につけていたので、今回も
同じ手順を踏んだ。その結果、**最初に書いた検査6の実装は、まさに検出
したかったバグ (`Partial<Email>`) を素通りさせる欠陥を持っていた**
(ジェネリクスの「宣言」と「使用」を正規表現で区別できず、使用側まで
ローカル定義として許可していた)。テストを書かずに「動くはず」で
済ませていたら、この検査は永久に何も検出しない飾りになっていた。

**教訓**: 検証コードを書いたら、その検証コードが実際に検出すべきものを
検出できるかを、書いた本人が確認する。「一般化した」「追加した」は
まだ成果ではなく、「検出できることを確認した」までが成果である。

## 追加問答 (2026-09・I5「PII をログに含めない」も無効だった)

**Q: I6 (unwrap 禁止) を検証して「守られている」と確認した後、なぜ
すぐ I5 も確認したのか?**

A: I6 の検証は「手を動かして初めて分かることがある」ことを再確認させた。
CLAUDE.md には他にも I1〜I5 の不変条件があり、どれも `#[deny(...)]` や
専用コンポーネントで強制する設計だが、`clippy`/`cargo test` が D20 で
動かない以上、**設計されているだけで一度も検証されていない不変条件が
他にもあるはず**だと考えるのが自然だった。

**Q: I5 は守られていたか?**

A: 二重の意味で守られていなかった。第一に、PII 検出用の `PrivacyLayer`
(`tracing_subscriber::Layer` として実装済み) が**どの subscriber にも
登録されておらず、実行時に一度も動いていなかった**。`kaname-ui` は
`kaname-observability` に依存していたが、実際に import していたのは
無関係な `TrajectoryMonitor` だけだった。第二に、登録したとしても
`PrivacyLayer` の docstring が主張する「PII 検出時にイベントをドロップ
する」は**実装されていなかった**。実際のコードは警告ログを追加発行する
だけで、PII を含む元のイベントは素通りしていた。`tracing-subscriber` の
`Layer::on_event` には他レイヤーへの伝播を止める権限が構造的に無く、
本当にブロックするには `Filter::event_enabled` ベースの再設計が要る。

**Q: 手動監査で「ログに PII を直接埋め込むコードは無い」と確認していた。
それでは不十分だったのか?**

A: 不十分である。それはプログラマの注意力のみに依存する保証であり、
`static-check.sh` のような機械的検証もかけていない (I5 は文字列内容の
意味論を要するため、I6 ほど単純に自動化できない)。だからこそ
`PrivacyLayer` という多重防衛層が設計されていたのに、それが完全に
無効だったことは見過ごせない。**「今のところ違反が無い」ことと
「違反を防ぐ仕組みが機能している」ことは別**であり、後者が無ければ
前者はいつまで持つか分からない。

**Q: 今回の修正で I5 は完全に守られるようになったか?**

A: なっていない。`PrivacyLayer` を実際の subscriber に組み込んだことで
「検知して警告する」ところまでは機能するようになったが、**検出しても
ブロックはしない**。真のブロックには `Filter` ベースの再設計が必要で、
ネットワークが無い現状の環境では `cargo check` による型検査もできない
ため着手を見送った。中途半端な状態を「直した」と言わず、残作業として
明記することが、このドキュメントの一貫した方針である。

## 追加問答 (2026-09・自分の分類をもう一度疑った結果)

**Q: D29 (settings_get の分類ミス) を直した直後、なぜ D24 (a) も
再検証したのか?**

A: D29 は「検証せずに書いた分類が1つ間違っていた」という具体例だった。
D24 は一度に37個のコマンドを仕分けており、(c) で1件間違えていたなら、
(a) の10件も本当にすべて確認して書いたのか、自分で疑うのが筋だった。

**Q: (a) は何が間違っていたか?**

A: 「LLM 依存だから配線しない」という一つの理由で10件を一括りにして
いたが、実装を読むと8件は `kaname-ai::llm_bridge` を一切呼んでいない
決定論的なチェッカーだった。本当に LLM 生成を要するのは2件だけ。
**「配線すると嘘になる」という強い理由と、8件の実態は違った。**

**Q: では8件をすぐ配線すべきか?**

A: しない。理由を差し替えた: 「配線したら嘘になるから」ではなく、
「まだ守るべき LLM 呼び出しが製品内に無いから」。`commands.rs` を
検索した限り、`llm_bridge`/`QuarantinedLlm`/`PrivilegedLlm` を実際に
呼ぶ経路は一つも無い。防衛策だけを先に UI へ繋いでも、守る対象が
存在しない「先出しの防具」になるだけである。結論 (配線しない) は
変わらなかったが、**理由が違えば、いつ配線すべきかの判断基準も違う**
— 「LLM がスタブでなくなったら」ではなく「LLM 呼び出し経路ができたら、
その入出力の境界として同時に組み込む」が正しい順序になった。

**教訓**: 結論が同じでも、理由が間違っていれば、次の判断を誤らせる。
一度書いた分類文書も、機会があれば手を動かして裏を取り直す価値がある。

## 追加問答 (2026-09-20・「修正済み」の表記をもう一度疑った結果)

**Q: PR #209 で「static-check の誤検出を状態機械化で解消」とマージされた。
安全網は直ったと言えるか?**

A: 部分的にしか言えない。#209 が直したのは検査2 (strip_noise) と
検査4 (注入引数) だけで、同じ字句解析欠陥を持つ検査6
(`strip_comments_and_strings` の正規表現カスケード) と検査7
(`strip_ts_noise` — Rust の r# パターンを TS に誤持込していた) は
未修正のまま残った。**「見つかった箇所を直す」と「同型欠陥を全て
潰す」は別の仕事**であり、前者だけで「解消」と読むのは早い。
合成テストで実証: doc コメント内の孤立 `"` が後続文字列とペア化して
本番 `.unwrap()` を見逃す (p1)、という I6 を黙殺する経路が残っていた。

**Q: `strip_single_test_fns` は動いていたか?**

A: **一度も動いていなかった**。パターン `[^\]]*\]?\s*\n` の
`[^\]]*` は改行を除外しないため、`#[test]` の後ろから文末近くまで
全てを「属性」として貪欲消費し、`src.find('{', m.end())` が常に
ファイル末尾を指して「ブレースなし」扱いになっていた。つまり
`#[cfg(test)]` mod の外に置かれた単体 `#[test]` 関数は1回も
除去されていなかった。たまたま現在のコードベースに「mod 外の
テスト内 unwrap」が無いため表面上グリーンだっただけで、
**存在するだけの検査**だった。

**Q: `[workspace.lints]` の deny は効いていたか?**

A: 効いていなかった。Cargo の workspace lints は member crate が
`[lints] workspace = true` を宣言しない限り継承されない。全24
パッケージが未宣言で、`await_holding_lock`/`await_holding_refcell_ref`
の「確実な実行時バグの静的検出」は書かれただけの死んだ設定だった。
全クレートに継承を追加し、MutexGuard を .await 跨ぎで保持する
合成違反で `-D clippy::await-holding-lock` が発火することを確認して
初めて「効いている」と言える。

**Q: なぜ「検出能力の合成テスト」にこだわるか?**

A: この1セッションで3件も「書いてあるが機能していない検査」が出た
からである。deny は未継承で死に、テスト除去は正規表現の貪欲で死に、
コメント除去は parity 反転で逆結果を出しうる。**検査コードは
「存在」ではなく「違反を実際に弾く」ことを持って初めて機能と呼べる。**
言い換えると、安全網自体が最大の盲点である。

**教訓**: 「修正した」というコミットメッセージも検証対象。
部分修正は全体修正と同じ顔をして現れる。同型欠陥は grep ではなく
「その欠陥クラスのパターンを全箇所に当てる」確認で潰す。


## 「DB は暗号化されている」とは、どうやって分かるか (D75)

**Q: kaname-store は暗号化されているか?**

A: ヘッダコメントは「暗号化ローカルストア。SQLite + SQLCipher (rusqlite)。
依存: rusqlite = { version = "0.32", features = ["sqlcipher",
"bundled-sqlcipher"] }」と明記し、`SqlCipherParams` は PAGE_SIZE /
KDF_ITER / HMAC / plaintext_header_size まで固定値で実装され、
`Store::open` は 64 桁 16 進鍵を検証し `PRAGMA key` を適用し、
PRAGMA 文字列を Zeroizing で包んでいた。これだけ丁寧な実装を
見れば「暗号化は動いている」と誰もが思う。

しかし workspace Cargo.toml の実際の依存は
`features = ["bundled"]` — **素の SQLite3** だった。
`PRAGMA key` も `cipher_*` も全て silent no-op で、
integrity_check は平文 DB に対して当然 "ok" を返し、
全テストは何事もなくグリーンだった。実測: `PRAGMA cipher_version`
は存在せず (空)、書き込んだスキーマとデータ文字列がファイル
本文に平文で残る。**アプリは起動し、全機能が動き、全テストが
パスする状態で、中核の約束である「ローカル暗号化」は一度も
成立していなかった。**

**Q: なぜ今まで誰も気づかなかったか?**

A: 全ての検証が「正しい操作がエラーにならない」方向でしか
なかったからである。鍵長検証・PRAGMA 実行・integrity_check は
「平文でも落ちない」ものばかり。ファイルの実バイトを見る検査は
存在しなかった。ソクラテス式に言えば「ストアが開ける」ことを
「暗号化されている」と読み違えていた —— **確認されたのは
開通であり、主張は秘匿性だった**。

**Q: 直して終わりか?**

A: `bundled-sqlcipher` に変えて `cipher_version = 4.5.3 community`、
本文から既知マーカー非出現を確認した上で、恒久回帰テスト
(`dbファイルは暗号化され既知文字列が平文で残らない`) を入れた。
feature を誰かが戻せばそのテストが即座に検出する。
なお残課題: 平文期間に作られた既存 history.db は新ビルドでは
開けない (cipher は平文を読まない)。プレリリースのため移行
コードは入れず、D75 に残課題として明記した。

**教訓**: セキュリティ主張の検証は「正しい時に動く」ではなく
「ファイル/ワイヤの実出力を見る」こと。丁寧に書かれた
パラメータ実装は、依存 feature 一個で無意味化しうる。

## ソクラテス問答 — 第19ラウンド (D91)

**主張**: 「添付はファイル名で対応付けてダウンロードできる」

**問**: ファイル名は一意か?

**答**: 一意ではない — 添付名は送信者が自由に名付ける。
同じ `invoice.pdf` を2件付けたメール (誤りでも悪意でも) では
`map[filename]` が後着で上書きされ、1件目のボタンを押しても
2件目の blob が降りる。

**問**: これは悪用できるか?

**答**: 軽度に — 添付1を無害な `report.pdf`、添付2を同名の
悪性 `report.pdf` とすれば、利用者は「添付1を開いたつもりで
添付2」を取得する。検査自体は両方に走るため is_dangerous は
表示されるが、ダウンロードの対応関係は壊れていた。

**教訓**: マップのキーは「それが一意である根拠」を持つべき。
ファイル名・表示名・件名のような「自由入力値をキーにする」
設計は、一意性が保証されない限り暗黙の上書きになる。

## 追加問答 (2026-09-20・「送信できた」を「正しく送れた」と読み違えていなかったか)

**Q: `send_email` が組み立てる生メッセージは RFC 5322 のヘッダー規則を満たすか?**

A: 満たさなかった。RFC 5322 のヘッダーは US-ASCII のみだが、
`Subject: {subject}` は生文字列をそのまま書いていた。日本語件名は
SMTPUTF8 非対応経路で文字化けする。「送信が成功する」テストは
あっても「ヘッダーが ASCII で構成される」検査は存在しなかった。
さらに本文も生 UTF-8 で `Content-Transfer-Encoding`/`MIME-Version`
が無く、7bit 前提の下流 MTA では本文破壊の可能性がある。

**Q: つまり日本語メールを正しく送れないプロダクトだったということか?**

A: 日本語を主対象とするメールクライアントが、日本語を規格どおりに
エンコードしないまま送信していた — そのとおりである。修正は
`encode_header_utf8` (RFC 2047 encoded-word) と本文 base64 +
`MIME-Version`/`CTE`。アドレス (From/To) は addr-spec であり
encoded-word は使えないため raw のまま — EAI アドレスは
SMTPUTF8 経路が前提となることをコメントに残した。

**Q: 他に無駄はあったか?**

A: `send_email` の `draft_id` パラメータは唯一の呼び出し元が
`None` 固定で、「送信後に下書き削除」分岐は一度も到達不能だった
(D95)。UI に下書き保存経路が存在しない以上、パラメータは
将来設計の亡霊であり、削除して実装時に git 履歴から復元すればよい。

**教訓**: 「生メッセージを組み立てる」コードは最も厳格な規格準拠が
求められる場所でありながら、テストは「通った/失敗した」のみで
ワイヤ上の実出力を規格と照合していなかった。送信系の検証は
「サーバが受け取ったか」ではなく「出したバイト列が規格に適合するか」。

**Q: 「ファジング済み」はどうやって確認するか?**
A: package.json に `fuzz:mime`/`fuzz:html`/`fuzz:prompt` が揃い、

## ラウンド 28 (2026-09-20)

**問い**: fuzz/corpus/ に置かれた種ファイルは、実際に何かを検証しているか?

**A**: 半分はしていなかった。6 コーパス中 3 件 (aitm_urls /
calendar_phishing / ssa_bypass) に対応する fuzz ターゲットが存在せず、
Storm-1747・Tycoon2FA 等の実観測攻撃パターンの種ファイルは
**書かれた時点から一度も実行されていなかった** (D103)。
workspace exclude の fuzz/ は全検査の死角であり (D98)、コーパスの
存在がターゲットの存在を保証しないことも見逃されていた。

**Q: 孤立していたのはコーパスだけか?**

A: 違う。ターゲットを新設して種を食わせた途端、aitm_urls の
コーパス1番目 (tycoon2fa_pattern.txt) が不変条件 `score <= 100`
を即座に違反 — `AitmRisk.score` の doc 契約「0-100」は虚偽で、
実装は無上限加算だった (D102)。**種が「検出するため」に書かれた
攻撃 URL が、スコア上限を突破して何も報告していなかった**。
verdict 閾値 (50) 自体は超過していて実害は限定的だが、契約文書と
実装の乖離はこの系譜の典型。`score.min(100)` でクランプし
doc 記述 (80+ → 50+) も実装に合わせた。

**Q: ssa_bypass の種は機能したか?**

A: はい。`EmailStyleFeatures::extract` は 500KB 切り捨て・
`send_hour % 24` 正規化・NaN 可能性を is_finite() で露出する
設計が正しく、1.13M exec でクラッシュゼロ。有限性を呼び出し側が
検査する契約も fuzz 側から固定した。

**教訓**: 検証資産 (シード/コーパス/テストケース) は「存在」ではなく
「実行経路が生きているか」で評価する。`fuzz/corpus/<name>` と
`fuzz_targets/<name>` の対応関係は1対1でなければ無意味であり、
今回のようにコーパスが先に書かれターゲットが忘れられる退行は
起きうる。

## ラウンド 35 — 「学習する」とは何を保存することか

**Q: SSA 文体認証は実装済みか?**

A: コードとしては実装済みだった — `evaluate_sender_style` は
`EmailStyleFeatures::extract` → `assess_self_send_anomaly` → 警告文
の完全なパイプラインを持ち、NaN 汚染防止・判定後取り込みの
自己汚染防止まで丁寧だった。しかし**プロファイルの置き場所が
プロセス内 HashMap だけ**だった。

**Q: インメモリでも動くのでは?**

A: 動かない。警告は `sample_count >= 10` からしか出ない。
平均的なユーザーが1セッションで同一送信者から10通処理することは
稀であり、再起動で全消去される限り**実運用では永久に
InsufficientData** — 「実装済み」の看板と「発火不能」の実態が
矛盾していた。学習系機能の「実装済み」は検出器の存在ではなく
**学習の蓄積が時間を跨いで生き残ること**を意味する。

**Q: なぜ settings テーブルか。専用テーブルではなく?**

A: プロファイルは「送信者→統計ベクトル」の key-value そのものであり、
汎用 settings (暗号化済み・account スコープ済み) で要件を満たす。
新スキーマを足すより既存の実効済み経路に乗せる方が小さい
(マスク式: まず部品を減らせ)。

## ラウンド 36 — 「修正した」とは何か (取りこぼしの再発)

**Q: この 2 週間で検出した欠陥は修正されたか?**

A: 台帳上は修正済みと記され、各修正には対応する PR とテストまで
あった。しかし `git log --all --not main` で実測すると
**~116 件のコミットが main の祖先に存在しなかった**。
「修正した」は「修正を提案した」であり、それは「修正が製品に
存在する」とは違う。

**Q: なぜマージされないまま閉じられた?**

A: 履歴の再構築とマージの遅延の複合。修正 PR が並走するうちに
main の履歴が書き換わり、各 PR の差分は「パッチとしては着弾」
(patch-id 一致) したものと「実際に失われた」ものに分かれた。
後者は ~45 件。patch-id が一致しないから失われた、ではない —
別経路で同等修正が入ったケースがあるため、**シンボルの実在を
grep で確認するまで「失われた」と断定できない**。

**Q: 検出器の修正が失われても、アプリは動くのでは?**

A: 動くが、約束を守らない。例: (a) 一覧と詳細で BEC 判定が
食い違う (D100 — 検証済み送信者のメールを開くとスコアが
「悪化」して見える)、(b) セッション応答 URL のオリジン未検査で
トークン流出経路が残存 (D83)、(c) `record_received` に件名を
話題プロファイルとして保存し「話題急変」シグナルが構造的に
誤発火 (D111)。**失われた修正は、それが修正した欠陥と同じく
不可視** — テストが無ければ再発に気付かない。

**Q: 二度目の取りこぼしはなぜ起きた? 一度目 (C8) で防げなかった?**

A: C8 は「孤児が存在する」事実の発見だったが、再発防止の検査は
仕組み化されなかった。今回の救出は手動の棚卸しに依存している。
根本対策は**マージされないまま閉じられた PR を一覧する定期検査**
(`gh pr list --state closed` で mergedAt=null) の仕組み化 —
D114 として登録。人間のマージ作業を信頼するワークフローは、
信頼するたびに欠落する。

**教訓**: マスク式「部品を減らせ」は git 履歴にも適用される —
作った修正は着弾して初めて部品として存在する。PR の存在は
修正の存在ではない。

## ラウンド 37 — 「繋がっている」とは何か (配線の実在確認)

**Q: 「コマンドが登録されている」は「機能が使える」と同じか?**

A: 同じではない。登録は `invoke_handler` への列挙にすぎず、
フロントエンドからの呼び出し経路が無ければ dead code。
逆に今回の検査では grep パターンが generics 付き呼び出し
(`invoke<T>("mail_download_attachment")` の複数行形式) を
見落とし、一時「4 コマンド未配線」と誤判定しかけた —
**計測器 (検索正規表現) 自身も検証対象**。
実測の結論: 27 コマンド全てに呼び出し経路が存在した。

**Q: クレートが workspace の members にあれば製品に入っているか?**

A: 入っていない。`kaname-ui` (製品エントリ) からの推移閉包を
Cargo.toml 実測すると到達は 16 クレート。`kaname-ai`・
`kaname-mls`・`kaname-sandbox` は member に残るが依存辺が
無い (kaname-ai は kaname-tests 経由のみ)。members 列挙は
「存在」、依存辺は「配線」— 両者は別の主張であり、後者を
検証しないと「作ったが組み付けられていない」状態を見逃す
(D19 がまさにこれだった)。

**Q: 「12分類器を実装済み」とは、12分類器が働いていることか?**

A: 違った (D57)。`run_classifier` は12分類器すべてを正しく
ディスパッチできるが、`default_rules()` が参照したのは3つだけ。
**実装は能力の存在を保証するが、既定値は能力の発動を決める**。
「できる」と「される」の間にルール表がある。
SSN・医療情報が既定で無検査のまま送信可能だった — 保護の
存在が保護の発動を意味しない典型例。今回6分類器を既定有効化し、
残り2つ (法人番号 = 公表情報、IP = 単体で非機微) は
見送り理由をコードに記録した。

**Q: 「古い差分を持っている」は「適用すべき差分がある」と同じか?**

A: 同じではない (D113)。孤児コミット 20b8ca2 は「44件の未使用
依存削除」を含んでいたが、救出作業中に対象 Cargo.toml が別経路で
整理済みだった。fresh な `cargo machete` 実走の結果はゼロ —
**依存宣言は時価であり、記録された差分ではなく現在の計測が真実**。
台帳の「未適用」表示が陳腐化していたもう一例。

## ラウンド 38 — 「安全に扱っている」とは何を確認することか

**Q: 「SQLCipher で暗号化している」は「鍵が安全」と同じか?**

A: 同じではない。暗号化アルゴリズムの正しさと鍵管理の正しさは
別の主張。実測: `history.key` が 0600 で DB と同じディレクトリに
置かれるファイル方式 (キーチェーン未統合) — しかし README/
maturity/D23 に「キーチェーン統合は未実装」と明記されており、
**弱い実装を正直に記述した設計**はギャップではない。
ギャップなのは「主張 > 実装」の場合のみ。

**Q: 「監査ログを書いている」は「監査が存在する」と同じか?**

A: 書き込み側だけでは不十分。`audit_event` は Store が None の
とき return していた — 書き込み API の存在は、失敗時の
可観測性まで含めて初めて「監査がある」と言える (D120)。
D23 と同型: 「失敗しても続行」は証跡の喪失を見えなくする。

**Q: 「モックサーバーがある」は「E2E が実バックエンドを叩く」と同じか?**

A: 同じではない。kaname-mockserver は make ターゲットとして
存在するが、playwright.config.ts の webServer には
「spec がまだ使っていないため削除」と注記されていた —
存在するテスト資産がテスト経路に繋がっているとは限らない。
ただしこれは未実装を装っていない正直な注記であり、
ギャップではなく「次の一手」の情報だった。

**Q: 監査で「問題なし」が続くのは監査が機能していない証拠か?**

A: 逆である可能性がある。本ラウンドの検証対象 (送信経路・
鍵管理・監査・トークン管理・e2e 資産) はすべて正直に実装・
記述されていた。過去のラウンドで「主張 > 実装」を潰してきた
結果、**残存するのは主張と実装が一致した部分**になる —
これは監査の失敗ではなく収束の兆候。ただし収束は
「監査対象の母集団が尽きた」ことと「見るべき所を見た」ことの
両方を確認して初めて言える。

## ラウンド 39 (2026-09): 「実装した」は再起動を越えられるか

**Q: D1 Phase 1 で openmls 化した MLS は、再起動後も機能するか?**

A: 機能しない — そして危険に見えた。`LibcruxProvider` の storage は
`MemoryStorage` 固定であり、グループ状態・署名鍵・`seen_welcomes`
(リプレイ防止帳簿) がすべてプロセス内メモリだった。つまり
**再起動するたびにリプレイ防止の帳簿が消え、同じ Welcome が
再受理される** — モック時代と同じ「存在するが効かない防御」が
本物の暗号の上に残っていた。

**Q: openmls が自分で永続化しないのか?**

A: しない。`MlsGroup` は操作のたびに `provider.storage()` へ書き、
再起動時は `MlsGroup::load(storage, group_id)` で復元する設計 —
つまり永続化は **ストレージバックエンド側の責務**。
`openmls_sqlite_storage` が既製の rusqlite 実装を提供しており、
workspace の bundled-sqlcipher rusqlite 0.37 とバージョンが一致した
ため、独自 `KanameProvider` で SQLCipher ファイルに載せられた。
残る勘所は署名鍵の復元 (`SignatureKeyPair::read` で openmls
storage から秘密鍵ごと引き戻す) と、openmls 管理テーブルと
kaname 帳簿 (会話メタ/seen_welcomes) の同一ファイル内
2 コネクション共有 (WAL + busy_timeout)。

**Q: 永続化した結果、モック時代より悪くなることは?**

A: リプレイ帳簿が永続化されたことで、**攻撃者にとって唯一の免罪符
(再起動によるリセット) が消えた**。一方 `kp_cache` はあえて揮発の
まま残した — 他人の公開 KeyPackage キャッシュは喪失しても再取得
可能で、永続化の攻撃面を増やす価値がない。削除すべきものを
削除するのもマスク式の一部。

**教訓**: 「暗号を本物にした」だけでは不十分 — 防御の**帳簿**
が揮発なら、防御は再起動で消える。Phase 1 の完了条件
(本番バイナリにモックを残さない) は満たしたが、
「動く」の定義に再起動が含まれていないと、セキュリティ上の
退化を見落とす。

## ラウンド 40 (2026-09): 「呼べる」は「届く」か

**Q: Phase 1-2 で実装した `MlsMailClient` は、メールを開いたユーザーに届くか?**

A: 届かなかった。クレート内で正しい暗号 (openmls/X-Wing) と正しい
永続化 (SQLCipher) があっても、`kaname-ui` が `kaname-mls` を依存に
持たず、IPC コマンドもゼロ、`analyze_raw_email` はエンベロープの
存在すら見ていなかった。つまり「実装した」暗号は出荷バイナリ内で
**一度も呼ばれない部品** — D12/D13/D21/D40 (実装済みだが未配線)
と同型だった。

**Q: 受信経路に挿すとき、失敗をどう扱うべきか?**

A: 「エンベロープがあるのに未初期化」をエラーにしてはいけない。
E2E はオプトインであり、mls_init していないユーザーのメール表示が
壊れると暗号化機能の存在自体が退行になる。同様にエンベロープの
解析失敗・復号失敗もメール全体の失敗ではなく「イベント」に降格させる
(暗号文メールを開けなくても、外側の本文と添付検査は成立する)。

**Q: `is_mls` バッジは今や正直か?**

A: このブランチでは「エンベロープが実際に抽出された」場合に立つ —
D116 (#252 の `is_mls_message`) と等価のカバレッジ。ただし D116 は
別ブランチの別実装であり、マージ時に統合が要る (同一の意図を 2 つの
コード経路で表現している — 後続で `extract_mls_envelopes` 側に
収斂させるのが正しい形)。

**教訓**: ライブラリの正しさと製品の正しさは別物。「呼び出せる API」
と「実際に呼ばれる経路」の間にあるのが配線 — モックを本物に替えても
配線が無ければ差はゼロ。
## ラウンド 41 (2026-09): 「配送経路」は添付で足りるか

**Q: KeyPackage 配送に専用サーバやディレクトリサービスは要るか?**

A: 要らなかった (マスク式: 要件を削除せよ)。設計書の推奨案どおり
`application/mls-key-package` 添付で自足する — メールは既に
「相手のメールボックスにバイトを届ける」唯一の到達経路を持ち、
KP 自身は公開情報 (署名公開鍵の束) で秘匿が要らない。残る攻撃面
(経路上の差し替え) は配送ではなく「どの KP を信頼するか」の問題で、
これは安全番号照合 (Phase 5) の責務として分離できた。

**Q: 添付送信は既存 `Email/import` 経路で足りたか?**

A: 足りた。`Email/import` は生 RFC822 blob をそのまま受け取るため
「添付 blobId を先に upload → Email/set で参照」という JMAP 標準手順
すら不要 — `multipart/mixed` を `build_raw_message` 内で組み立てる
だけで blobId 配管を一切増やさずに済んだ (削除できる設計の好例)。
ただしこの判断を下すには「実際の `send_email` が何を呼ぶか」の実測
が先に必要だった — 宣言された API 名から配管を推測するのは誤り。

**Q: 暗号化経路で DLP をどう両立させるか?**

A: 外側メールで DLP を評価すれば、エンベロープ内に封入された
実件名・本文は空に見えて素通りになる (E2E 化が情報漏洩防止を
実効的に無効化する逆効果)。`send_mail_core` に `dlp_target` を
分離して「送信されるもの」と「評価されるもの」を別引数にした —
暗号化前の実内容で評価する、という形だけが両立を成立させる。

**Q: `mls_start_conversation` の失敗順序は安全か?**

A: 当初は KP 消費 → 会話作成 → 送信失敗で「消費済み KP・会話だけ残り
Welcome は未配送」の中途半端な状態になり得た。JMAP 接続確認を
消費の前に移した — 「取り消し不能な操作は、失敗し得る操作の
後ろに置く」という順序の問題であり、型では守れない。
## ラウンド 42 (2026-09): 「照合した」をコンピュータはどう知るか

**Q: 安全番号セレモニーで「照合した」という事実はどこに住むべきか?**

A: MLS DB (mls.db) ではなく履歴 Store (history.db) 側の
`mls_conversations` 行に置いた。理由: (1) その列
(`safety_number`/`safety_number_verified_at`) が既にスキーマに
存在していた — 設計済みシームの D69 クラス、(2) 照合は「この
アカウントの利用者が別経路で確認した」という人的事実であり、
openmls のグループ状態とは別の記録対象。両者を混ぜると
再起動・再作成で照合記録がグループ状態に付き纏う。

**Q: 「未検証」と「番号が変わった」を同じ警告にしてよいか?**

A: いけない。未検証は「まだ照合していない」通常状態、
番号変更は「照合済みのはずが異なる」異常事態 — 同じ黄色に
塗ると中間者攻撃を未検証状態と見間違える。`verified` と
`safety_changed` を別フラグにしたのは「偽の警告」と
「真の警告」を型で分けるためである (D23/D34 の「主張>実装」と
同じく、警告の信用性はエラー表示の粒度に依存する)。

**Q: Store が無いとき verified をどう返すか?**

A: false。Store 未接続で verified=true を返すことはあり得ない
(記録そのものが存在しない)。逆に「Store が無いので検証できない」
ことを verified=false で偽るのは許容できる — ユーザーへの
メッセージは「まだ照合していない」であり、実際に照合記録が無い
以上、それは事実として正しい。

**教訓**: 「照合した」という人間の行為は、システムにとって
「この番号とこの時点を紐付けた記録」でしかない。セレモニーの
実体は UI ではなく永続化された不変の比較対象である。
## ラウンド 43 (2026-09): 「隔離」は型か、プロセスか

**Q: `Content<Untrusted>` の型境界が I1 を保証するとき、
インプロセスの `LocalLlmRunner` に本文を渡すのは違反か?**

A: 型の上では違反ではない — `bec_score` は正当な経路だった。
だが I1 の目的は「敵対的入力が届くコードを攻撃面から除く」ことであり、
llama.cpp は巨大な C++ パーサである。GGUF やトークナイザのバグが
あれば、ホストプロセス = アドレス帳・復号鍵・JMAP セッションを
持つプロセスが即座に侵害される。型は「誰が呼べるか」を守るが、
「落ちてもよい場所に落ちる」ことは守らない。サブプロセス化は
I1 の意図を物理層まで下ろす修正である。

**Q: サブプロセス化の対価は何か。正当化できるか?**

A: (1) 1 推論あたり JSON シリアライズの往復 (µs オーダー —
推論自体が秒オーダーなので無視できる)、(2) ワーカーの寿命管理
(Drop kill・EOF 検出・タイムアウト) の複雑さ、(3) 配布物に
2 つ目のバイナリ (externalBin + triple 接尾辞) が増える。
いずれも「不信入力を別プロセスの別アドレス空間に置く」利益に
見合う。対価が最も大きいのは (3) で、リリース手順に残課題がある。

**Q: モックフォールバックを spawn に残していいのか?**

A: `spawn` がモデル不在で `spawn_mock` (`true` プロセス + 既定
応答) に落ちる設計はテスト容易性のためのもので、本番呼出側が
`check_model` Ready を先に確認しないと「起動したが推論は固定
応答」の偽装になる。Ready ゲートを `ai_llm_start` に置いたのは
「便利な既定値が沈黙の偽装を生む」という反復する教訓 (D120 の
監査破棄、Phase 3 の EOF 偽装と同型) への対応である。

**教訓**: セキュリティ設計の「隔離」は、型・規約・プロセスの
どの層で主張されているかを常に確認する。型レベルの隔離は
コンパイラが守る。プロセスレベルの隔離は配線が守る。
片方だけが真なら、もう片方は飾りである。
