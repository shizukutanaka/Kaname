# ソクラテス問答による製品レビュー (2026-07)

イーロン・マスクのアルゴリズム (要件を疑う→削除→簡素化→組み立て) に加え、
**ソクラテス問答法** (前提を問い直す自問) で Kaname を批判的に吟味した記録。
誇張せず、実コードの根拠に基づいて長所・短所・改善点を並べる。

---

## Q1: この製品は「メールクライアント」と呼べるか?

**A**: 呼べる。v0.5.0 で受信 (`mail_fetch`) → 保存 (`save_message`) →
表示 (`sanitize_html`→`to_srcdoc`) → 送信 (`mail_send`, 送信前 DLP) →
検索 (`mail_search`) → 添付ダウンロード (`mail_download_attachment`) が
すべて配線された。ローカル `.eml` 解析はサーバなしでも動く。

**ただし**留保がある: 中核の暗号 (MLS) と LLM 推論はモック/スタブ (D1/D2)。
「セキュア**メール**クライアント」の「メール」部分は成立したが、
「セキュア」の暗号面は未達。→ 名乗るなら「**メールセキュリティ解析ツール
+ 実験的メールクライアント**」が正確。

## Q2: 「セキュリティ」は本物か、それとも見せかけか?

**A**: 検出ロジックは**本物**。BEC (9 決定論シグナル)・DLP・quishing・
添付検査 (MIME偽装/polyglot/危険拡張子/SVG/カレンダー)・リンク評判・
文体認証・トラッキング検出は、すべて実データで動き、判定に乱数も
固定値もない。サンプル `examples/emails/` で誰でも再現できる。

**見せかけの部分**: Dual-LLM の型境界は「定義は堅牢だが実装が通っていない」
(D17)。現状 LLM 経路が繋がっていないので悪用余地は無いが、
**LLM を繋ぐ前に D17 を塞がないと型保証が名ばかりになる**。

## Q3: 最大の弱点は何か?

**A**: **一度も `cargo check` を通していない** (D20)。
組織のエグレスポリシーで `static.crates.io` が遮断され、依存を取得できない。
`rustc` 直接実行による構文チェックと `scripts/static-check.sh` までが限界で、
借用チェッカ・トレイト解決・テストは未検証。

この穴は**実害を生んだ**: PR #64 の編集で関数が定義ごと消え、
コンパイルエラーの状態が 5 PR 検出されなかった (PR #70 で修正)。
→ これは製品の設計欠陥ではなく**環境制約**。ただしリリース品質を
主張するには型検査が必須であり、ネットワーク解放が最優先の残課題。

## Q4: 「完成」とは何を指すべきか?

**A**: 環境制約下で到達可能な完成は
「**ローカルで実メールを解析でき、サーバ接続時は送受信・保存・検索・
添付取得も動く、正直なプレリリース**」。
配線 (D10) はこのフェーズで完全に閉じた。
残る D1 (MLS)・D2 (LLM)・D20 (型検査) は**いずれもネットワーク解放が前提**で、
その旨を `maturity.md` に明記している。**できることとできないことを
偽らずに示せている状態を「完成」と定義する**。

## 長所 (実コード根拠あり)

- 検出ロジックが世界水準かつ決定論的で、2026 年の最新脅威 (DKIM リプレイ・
  動的QR・SVG マルチモーダル注入・表示名ホモグラフ) を反映
- 「モックを本物と偽らない」規律: `kaname-mls`/`kaname-sandbox` を
  到達可能クレート数のために繋がず、暗号/隔離を装わない
- 判定不能を「安全」と偽らない (UNKNOWN / InsufficientData を SAFE にしない)
- 新規外部依存をほぼ増やさず (日付計算も自前)、攻撃面を広げていない

## 短所

- 型検査未実施 (D20、環境制約)
- MLS がモック・LLM がスタブ (D1/D2)
- Dual-LLM 型境界の実装が定義を通っていない (D17)
- 認証トークンを永続化しないため起動のたびに再接続が必要 (OS キーチェーン未統合)

## 改善点 (優先順)

1. **ネットワーク解放後に `cargo check --workspace` + `cargo nextest`** で
   本セッションの全コミットを一括検証 (D20)
2. **D17 を塞ぐ**: `llm_bridge` の実装を `dual_llm` の trait に載せ替え、
   `Content` の serde 偽造穴を閉じる — LLM を繋ぐ前に必須
3. **MLS を `openmls` で実装** (D1)、PQ ciphersuite を最初から選定
4. OS キーチェーン統合でトークンを安全に永続化

## 追加問答 (2026-09・フロントエンド到達可能性)

**Q: 「配線した」と言えるのは、いつか?**

A: 前セッションで「受信箱の検索欄を `mail_search` に接続した」「送信時に DLP が
ブロックする」と記録したが、**どちらもエントリポイントから到達できなかった**。
`Inbox.tsx` はどこからも import されておらず、受信トレイに実際に描画されていたのは
invoke を一切呼ばない `KanameDesign` だった。`mail_send` を呼ぶ画面も未到達だった。

つまり「コマンドを呼ぶコードを書いた」ことと「製品がそのコマンドを呼ぶ」ことは
別である。**「配線した」と言えるのは、エントリポイントからの到達可能性を実測した
ときだけ**である。クレートについては D19 で依存グラフを実測して同じ病を見つけて
いたのに、フロントエンドに同じ計測を適用していなかった。

**Q: なぜ同じ間違いを繰り返したのか?**

A: 計測の対象を「自分が今書いているレイヤー」に限定していたから。Rust 側の
到達可能性は測ったが、TypeScript 側は「ファイルが存在し、正しいコマンドを
呼んでいる」ことを確認して満足していた。**存在は到達可能性を意味しない。**

**Q: この発見は製品にとって良い知らせか、悪い知らせか?**

A: 良い知らせである。実装は既に存在し、欠けていたのは import 1 行と
引数の形だけだった。悪いのは**発見が遅れたこと**であって、実装ではない。
そして削除できるコードが 2,284 行見つかった — モック専用の画面 2 つは、
実データ版が動く以上、存在するだけで「どちらが本物か」を曖昧にする負債だった。

**Q: では今、UI は正直か?**

A: 一点、明確な嘘を見つけて直した。作成画面の MLS インジケータは宛先ドメインの
接尾辞 (`@kaname.app`) だけを見て「MLS 対応」と表示していたが、`kaname-mls` は
XOR モック (D1) であり、宛先が何であれ実際の暗号化は行われない。
**実装されていない保護を UI が「対応済み」と示すのは、検出ロジックの精度を
誇張するより悪い** — 利用者はそれを見て機微な情報を送るからである。常に
非対応を返すよう修正した。

オンボーディング画面を配線しなかったのも同じ理由による。`settings_save_onboarding`
はエラーを返すスタブであり、配線すれば「設定が保存できたように見えて失敗する」
画面になる。**保存できない設定画面は、無い方がよい。**

**Q: 到達可能にすれば十分か?**

A: 不十分だった。`Inbox` を出荷 UI にした直後に、その `Inbox` が呼ぶ 3 コマンドが
すべてスタブだと分かった。到達可能性は必要条件であって十分条件ではない。
検証は「エントリポイントから到達できるか」と「到達先が実装か」の**二段**で行う。
今回は「到達可能 UI が呼ぶコマンド ∩ `not_wired` スタブ」を機械的に求め、
空集合になるまで実装した。

副産物として、作成画面に定型文を「AI 草案」と称して挿入するボタンを見つけて
削除した。LLM がスタブである以上、それは AI 出力の偽装である。

**Q: 「実装した」と記録した永続化は、動いていたか?**

A: 動いていなかった。二重に。Store を開くコマンドはどの UI からも呼ばれておらず、
仮に開いても外部キー制約の前提となる `accounts`/`mailboxes` 行を作る本番コードが
無かった。「Store 未接続なら何もしない」「保存に失敗しても解析結果は返す」という
安全側の設計が、**欠陥を完全に隠していた**。エラーが出ないことは動いている証拠に
ならない。ログに warn は出ていたはずだが、誰も見ないログは無いのと同じである。

**Q: では完成とは?**

A: エントリポイントから到達可能な UI (9/9) が呼ぶコマンドがすべて実装
(`not_wired` 0 件) で、その実装が外部キーやセッション等の**前提条件を自分で満たす**
こと。今回の修正でその状態に達した。残るのは環境制約 (cargo 未検証・D20) と、
最初から「モック」と明示している MLS/LLM/サンドボックスであり、
それらは**製品が嘘をつかない限り**完成の定義に含めない。

## 追加問答 (2026-09・計測の自動化)

**Q: なぜ同じクラスの間違いを 4 回繰り返したのか?**

A: 毎回「その場で python を書いて測り、直したら測定を捨てていた」から。
死蔵コンポーネント・引数不一致・スタブ呼び出し・Store 未オープンは、
どれも**機械的に検出できたはずのクラス**である。人間の注意力に頼る限り、
次のセッションでまた見落とす。

マスクのアルゴリズムの第 5 段階「自動化」は、削除と簡素化が済んでから
行えという順序である。v0.6.0 でそれが済んだので、`scripts/static-check.sh`
に検査 3 (フロントエンド到達可能性)、検査 4 (invoke とコマンド定義の
名前・引数の整合)、検査 5 (登録済みだが呼ばれないコマンド) を恒久化した。

**Q: 自動化して、すぐ何か見つかったか?**

A: 実行した瞬間に 3 件見つかった。`AdminDashboard` は**どこからも描画されず**、
存在しない 3 コマンド (`admin_get_dashboard` ほか) を呼んでいた。
`mail_list` は**空配列を返す偽実装**で、呼び手はゼロだった。
どちらも削除した。ファイル単位の到達可能性 (検査 3) では見つからない、
**ファイルは到達可能だがコンポーネントは死んでいる**という細かい欠陥だった。

**Q: 「UI が呼ぶ先はすべて実装」で完成と言えるか?**

A: 言えない。逆方向を測っていなかった。検査 5 は、登録 37 コマンドのうち
**19 件が UI から呼ばれない**ことを示した (D24)。ただしその内訳は重要で、
10 件は LLM 依存であり、**LLM がスタブの現状で配線すれば偽の AI 出力を
表示することになる**。配線しないことが正しい。残り 5 件は配線すべきもの、
4 件は内部 API として正当なものである。

**完成とは「全部つながっている」ことではなく、「つながっていない箇所の
理由を全部言えて、その理由が正当である」ことだと考える。**

## 追加問答 (2026-09・検証ツール自体の欠陥)

**Q: `static-check.sh` は本当に安全網として機能していたか?**

A: していなかった。PR #86 で `mail_list` を削除した際、同じ関数を呼ぶ
テストが2件、コンパイルエラーのまま次のセッションまで残っていた。
`static-check.sh` の検査2はまさにこの種の回帰 (関数を削除したのに
呼び出しだけが残る) を検出するために作った検査だったが、実装が
**ハードコードされたシンボル一覧**しか見ておらず、一覧に `mail_list`
が無かったために素通りしていた。検証ツール自身が「一覧を都度手で足す」
という、検出したかった問題と同じ構造の脆さを抱えていた。

**Q: なぜ一般化を後回しにしていたのか?**

A: PR #71 で最初に作った時点では「今回壊れた具体的な関数名を拾えれば
十分」という最小実装で止めていた。その後 D21/D22/D24 の一連の配線作業で
検査3〜5を追加したが、検査2自体は一度も見直していなかった —
新しい種類の欠陥を追加するたびに検査を増やす一方、既存の検査の
弱点を遡って直す習慣がなかった。

**Q: 一般化したら何が起きたか?**

A: 最初の実装はリポジトリ全体で70件超の誤検知を出した。原因を1つずつ
潰す過程で、属性・raw文字列・char リテラル・行末コメント・複数行 import・
クロージャ束縛という6種類の見落としが見つかった。特に文字列内の
バックスラッシュ行継続 (`\` + 改行) を1箇所見逃しただけで、そこから
後のファイル全体で文字列の境界がズレるという、デバッグに最も時間を
要した種類のバグだった。**検証コード自体にも、検証すべきコードと
同じだけの注意が要る。**

## 追加問答 (2026-09・同じ欠陥がフロントエンドにもあった)

**Q: D25 (Rust 側の放置されたコンパイルエラー) を直した後、同じ穴が
フロントエンドにも無いか確認したか?**

A: していなかった。指摘されたわけではなく、「他に価値ある小さな改善は
ないか」と自分で探した結果見つかった。`app.test.ts` の `makeEmail()` は
`KanameApp.tsx` 削除時に一緒に消すべきだった死蔵コードで、しかも削除済み
の `Email` 型を import せず参照していた。`tsc`/`vitest` が動く環境なら
型エラーで即発覚するが、D20 (ネットワーク遮断) で3セッション気付かれ
なかった。

**Q: 検査を追加する際、最初の実装をそのまま信用したか?**

A: しなかった。D25 で「一般化した検査自体に見落としがないか、合成的に
既知のバグを再現して確認する」という手順を身につけていたので、今回も
同じ手順を踏んだ。その結果、**最初に書いた検査6の実装は、まさに検出
したかったバグ (`Partial<Email>`) を素通りさせる欠陥を持っていた**
(ジェネリクスの「宣言」と「使用」を正規表現で区別できず、使用側まで
ローカル定義として許可していた)。テストを書かずに「動くはず」で
済ませていたら、この検査は永久に何も検出しない飾りになっていた。

**教訓**: 検証コードを書いたら、その検証コードが実際に検出すべきものを
検出できるかを、書いた本人が確認する。「一般化した」「追加した」は
まだ成果ではなく、「検出できることを確認した」までが成果である。

## 追加問答 (2026-09・I5「PII をログに含めない」も無効だった)

**Q: I6 (unwrap 禁止) を検証して「守られている」と確認した後、なぜ
すぐ I5 も確認したのか?**

A: I6 の検証は「手を動かして初めて分かることがある」ことを再確認させた。
CLAUDE.md には他にも I1〜I5 の不変条件があり、どれも `#[deny(...)]` や
専用コンポーネントで強制する設計だが、`clippy`/`cargo test` が D20 で
動かない以上、**設計されているだけで一度も検証されていない不変条件が
他にもあるはず**だと考えるのが自然だった。

**Q: I5 は守られていたか?**

A: 二重の意味で守られていなかった。第一に、PII 検出用の `PrivacyLayer`
(`tracing_subscriber::Layer` として実装済み) が**どの subscriber にも
登録されておらず、実行時に一度も動いていなかった**。`kaname-ui` は
`kaname-observability` に依存していたが、実際に import していたのは
無関係な `TrajectoryMonitor` だけだった。第二に、登録したとしても
`PrivacyLayer` の docstring が主張する「PII 検出時にイベントをドロップ
する」は**実装されていなかった**。実際のコードは警告ログを追加発行する
だけで、PII を含む元のイベントは素通りしていた。`tracing-subscriber` の
`Layer::on_event` には他レイヤーへの伝播を止める権限が構造的に無く、
本当にブロックするには `Filter::event_enabled` ベースの再設計が要る。

**Q: 手動監査で「ログに PII を直接埋め込むコードは無い」と確認していた。
それでは不十分だったのか?**

A: 不十分である。それはプログラマの注意力のみに依存する保証であり、
`static-check.sh` のような機械的検証もかけていない (I5 は文字列内容の
意味論を要するため、I6 ほど単純に自動化できない)。だからこそ
`PrivacyLayer` という多重防衛層が設計されていたのに、それが完全に
無効だったことは見過ごせない。**「今のところ違反が無い」ことと
「違反を防ぐ仕組みが機能している」ことは別**であり、後者が無ければ
前者はいつまで持つか分からない。

**Q: 今回の修正で I5 は完全に守られるようになったか?**

A: なっていない。`PrivacyLayer` を実際の subscriber に組み込んだことで
「検知して警告する」ところまでは機能するようになったが、**検出しても
ブロックはしない**。真のブロックには `Filter` ベースの再設計が必要で、
ネットワークが無い現状の環境では `cargo check` による型検査もできない
ため着手を見送った。中途半端な状態を「直した」と言わず、残作業として
明記することが、このドキュメントの一貫した方針である。

## 追加問答 (2026-09・自分の分類をもう一度疑った結果)

**Q: D29 (settings_get の分類ミス) を直した直後、なぜ D24 (a) も
再検証したのか?**

A: D29 は「検証せずに書いた分類が1つ間違っていた」という具体例だった。
D24 は一度に37個のコマンドを仕分けており、(c) で1件間違えていたなら、
(a) の10件も本当にすべて確認して書いたのか、自分で疑うのが筋だった。

**Q: (a) は何が間違っていたか?**

A: 「LLM 依存だから配線しない」という一つの理由で10件を一括りにして
いたが、実装を読むと8件は `kaname-ai::llm_bridge` を一切呼んでいない
決定論的なチェッカーだった。本当に LLM 生成を要するのは2件だけ。
**「配線すると嘘になる」という強い理由と、8件の実態は違った。**

**Q: では8件をすぐ配線すべきか?**

A: しない。理由を差し替えた: 「配線したら嘘になるから」ではなく、
「まだ守るべき LLM 呼び出しが製品内に無いから」。`commands.rs` を
検索した限り、`llm_bridge`/`QuarantinedLlm`/`PrivilegedLlm` を実際に
呼ぶ経路は一つも無い。防衛策だけを先に UI へ繋いでも、守る対象が
存在しない「先出しの防具」になるだけである。結論 (配線しない) は
変わらなかったが、**理由が違えば、いつ配線すべきかの判断基準も違う**
— 「LLM がスタブでなくなったら」ではなく「LLM 呼び出し経路ができたら、
その入出力の境界として同時に組み込む」が正しい順序になった。

**教訓**: 結論が同じでも、理由が間違っていれば、次の判断を誤らせる。
一度書いた分類文書も、機会があれば手を動かして裏を取り直す価値がある。

## 追加問答 (2026-09-20・「グリーンの安全網」を疑った結果)

**Q: gap-analysis には「静的検査 8/8 グリーン」と書かれていた。
本当にグリーンだったのか?**

A: 違った。main 上で `bash scripts/static-check.sh` を実走すると
検査2 (`accounts()`/`strftime()` 等の未定義呼び出し誤検知) と
検査4 (`app` 引数不足の誤検知) が NG を出していた。
ドキュメントの「グリーン」は修正前の一時点の記録であり、
その後 main で静かに壊れていた。**CI が無い (D7/D63) ため、
安全網の故障は誰にも通知されない** — 監視系が死んでも
「監視系を監視するもの」が存在しない。

**Q: なぜ「正規表現で文字列を消してからコメントを消す」方式を
残さず、字句解析に置き換えたか? (マスク式: 要求を疑え)**

A: 除去の順序自体が構造的欠陥だった。文字列を先に消すと
doc コメント内の孤立 `"` (`表示名の \`"\` は除外する`) で
parity が反転し、文字列以降の全領域の内外が入れ替わる。
順序を逆にしても文字列内の `//` で同様に破綻する。
「どちらを先に消すか」という設計問題ではなく
「正規表現カスケードでは Rust の字句は扱えない」が答えだった。
検査2/6/7 がそれぞれ独自の strip 関数を持つ重複も含めて削除し、
`scripts/source_strip.py` の単一パス tokenizer に集約した。
(マスク式第2段: 簡素化 — 3つの strip を1つに。)

**Q: 検査6 (unwrap 検査) は本当に「本番コードだけ」を見ていたか?**

A: 見ていなかった可能性がある。旧実装は `#[cfg(test)]` mod の
ブレース対応を**生ソース**で取っていたため、テスト内に `"}"` を
含む文字列があると mod が早期に閉じ、以降のテストコードが
「本番」と誤認される (unwrap 誤検知)。逆に parity 反転が起きると
本番の unwrap がマスク側に飲まれ**見逃される**。検査は両方向に
嘘をつきうる状態だった。修正版は文字列/コメントを mask した上で
ブレース対応を取るため、文字列内容に引きずられない。

**Q: 「検査コードを直した」とは何をもって言えるか?**

A: このリポジトリの規律通り「実際に検出できることを確認するまで」。
合成ファイルで以下を実測した:
- 孤立 `"` を含むコメントの後の未定義呼び出し → 検出 (旧: 見逃し)
- 文字列内 `"}"` を含むテストの後の本番 `.unwrap()` → 検出
- 文字列内の `.unwrap()` → 非検出 (誤検知なし)
- `use tauri::AppHandle` 型の注入引数 → 非検出 / 実引数不一致 → 検出

**教訓**: 「安全網がある」ことと「安全網が機能している」ことは別物。
グリーンの記録は信用ではなく検証対象。CI 不在の環境では、
検査スクリプト自体を定期的に実走し直すことが唯一の保険になる。
